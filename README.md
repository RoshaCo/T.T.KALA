# ۳. شماره موبایل

شماره موبایل قبل از پرداخت دریافت نمی‌شود.

بعد از پرداخت موفق، کاربر فقط یک شماره موبایل وارد می‌کند.

فرمت معتبر:

09303933007

یا:

۰۹۳۰۳۹۳۳۰۰۷


شماره باید:

- ۱۱ رقم باشد
- با 09 شروع شود
- بعد از ثبت موفق، برای همان سفارش دوباره قابل تغییر نباشد


# ۴. جلوگیری از ثبت دوباره شماره

Backend باید برای هر سفارش فقط یک بار امکان ثبت موبایل بدهد.

مثلاً:

Order #123
mobile = null

کاربر شماره را وارد می‌کند:

09303933007

پس از ثبت:

Order #123
mobile = 09303933007

از این لحظه هر درخواست بعدی برای تغییر شماره همان سفارش باید رد شود.


# ۵. شانس

هر خرید موفق:

1 خرید
=
1 شانس


اگر یک شماره موبایل در یک دوره چند خرید موفق داشته باشد:

2 خرید
=
2 شانس

3 خرید
=
3 شانس


شانس فقط متعلق به دوره جاری است.


# ۶. دوره‌های قرعه‌کشی

فصل‌ها:

بهار:
1 فروردین تا 31 خرداد

تابستان:
1 تیر تا 31 شهریور

پاییز:
1 مهر تا 30 آذر

زمستان:
1 دی تا پایان اسفند


پس از پایان یک دوره:

شانس‌های دوره قبلی نباید وارد دوره جدید شوند.


مثال:

دوره تابستان:

mobile = 09303933007
chances = 3

با شروع پاییز:

chances = 0

تا زمانی که خرید جدید انجام شود.


# ۷. جستجوی شانس

کاربر فقط شماره موبایل را وارد می‌کند.

Backend باید فقط دوره جاری را بررسی کند.

اگر خرید موفق وجود داشته باشد:

خریدار است.

اگر خرید موفق وجود نداشته باشد:

غیرخریدار است.


Frontend فقط دو نتیجه کاربری دارد:

نتیجه اول:

شما در قرعه‌کشی شرکت داده شده‌اید.


نتیجه دوم:

شما هنوز در این دوره وارد نشده‌اید.


در نتیجه دوم باید گفته شود:

برای شرکت در قرعه‌کشی فقط کافی است یکی از محصولات ۲۹٬۰۰۰ تومانی را خریداری کنید.


# ۸. کد پیگیری

پس از پرداخت موفق، Backend برای سفارش کد پیگیری تولید می‌کند.

کد پیگیری فقط برای نمایش و سوابق است.

کاربر برای مشاهده شانس خود نیازی به وارد کردن کد پیگیری ندارد.

جستجوی شانس فقط با موبایل انجام می‌شود.


# ۹. امنیت پرداخت

Frontend هرگز نباید موفقیت پرداخت را قطعی اعلام کند.

فقط Backend باید Verify زرین‌پال را انجام دهد.

ترتیب:

Request
→
Payment
→
Callback
→
Verify
→
PAID


بدون Verify موفق:

order.status !== PAID


و هیچ شانس و لینک دانلودی ایجاد نشود.


# ۱۰. جلوگیری از پرداخت و سفارش تکراری

Backend باید از ایجاد سفارش‌های تکراری ناشی از:

- دوبار کلیک
- Refresh
- Callback دوباره
- درخواست تکراری
- Verify دوباره

جلوگیری کند.

پرداخت موفق باید idempotent باشد.


# ۱۱. لینک دانلود

لینک فایل محصول نباید مستقیماً در HTML عمومی سایت قرار بگیرد.

دانلود فقط برای سفارش PAID مجاز است.

Backend باید قبل از ایجاد لینک دانلود بررسی کند:

order.status === PAID


لینک دانلود بهتر است:

- موقت
- امن
- غیرقابل حدس
- دارای زمان انقضا

باشد.

# ۱۹. تراکنش دیتابیس

ثبت پرداخت و ثبت شانس باید به شکل Transaction انجام شود.

هدف:

اگر پرداخت موفق شد ولی ثبت شانس با خطا مواجه شد، سیستم نباید وضعیت ناقص و ناسازگار ایجاد کند.


# ۲۰. اصل مهم

هیچ داده‌ای از Frontend قابل اعتماد نیست.

Backend باید خودش بررسی کند:

- محصول معتبر است؟
- قیمت واقعی محصول چیست؟
- دوره فعال است؟
- سفارش متعلق به همین کاربر/پرداخت است؟
- پرداخت Verify شده؟
- سفارش قبلاً PAID شده؟
- شماره موبایل معتبر است؟
- شماره قبلاً برای همین سفارش ثبت شده؟
- دانلود برای این سفارش مجاز است؟

تمام تصمیم‌های مهم باید در Backend گرفته شوند.
